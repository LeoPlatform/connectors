# Plan: Build and Test the Datalake (Databricks) Connector

## Context

`connectors/datalake/` is the main deliverable of the EDW Redshift→Databricks migration: a new RStreams connector library that mirrors today's Redshift loader pipeline but writes Delta tables in Unity Catalog. As of today the directory contains only `CLAUDE.md` and `docs/project-principles.md` — no code, no `package.json`. The Redshift pipeline must remain independently deployable throughout; the datalake connector is an additive sibling, not a replacement.

This plan covers **Deliverable #1 only** (locked with Paul): the entity-group queue loader as a library package. VARIANT event tables and the retabulation library are deferred. The `offload_to_datalake.js` bot that wraps this library is also out of scope, but the plan leaves a clean seam so the bot can call the library the same way `general/lib/offload_to_redshift.js` calls `leo-connector-postgres/lib/dwconnect.js` today.

Locked decisions:
- **Model on `connectors/postgres`, not `connectors/redshift`.** The producer/offload path goes through `leo-connector-postgres` (specifically `lib/dwconnect.js`); `leo-connector-redshift` is only used by the `report/` consumer. `postgres/lib/dol.js` is a strict superset of the redshift version and is the right port template.
- **SQL gen** — adapt the Postgres DOL pattern (`connectors/postgres/lib/dol.js`) for Databricks dialect.
- **Databricks client** — official `@databricks/sql` Node SQL driver against a SQL warehouse.

### Step 3 — `lib/connect.js`: real Databricks query path
- `connect(opts)` opens `DBSQLClient`, calls `connect({host, path, token})`, opens a session with `initialCatalog`, `initialSchema`, session config `{ansi_mode:'false', infer_timestamp_ntz_type:'true', timezone:'UTC'}`.
  - **`ansi_mode=false`** intentionally mirrors Redshift's lenient cast/arithmetic semantics for coexistence equivalence. The loader does no arithmetic itself — it CASTs and MERGEs — but bad rows that Redshift COPY would have permissively tolerated (via `ACCEPTINVCHARS`/`ACCEPTANYDATE`) must not throw here, or Step 12 byte-equivalence fails. Strict mode is a modernization choice to revisit after Redshift retires; do not flip on as a side effect.
  - **`timezone='UTC'` + `infer_timestamp_ntz_type=true`** are paired to avoid introducing a third timezone shift on top of the existing enterprise correction chain (OS-Eastern → CUP-Pacific → enterprise-Eastern). The connector reads/writes only `TIMESTAMP_NTZ`; session TZ does not enter the stored value.
- `query(sql, params, cb, opts)` executes async, fetches all rows, returns `(err, rows, fields)` matching pg interface. Binding is positional `?` (note diff vs pg `$1`).
- `describeTables(cb, schema)` uses `SELECT … FROM <catalog>.information_schema.columns WHERE table_schema = ?`. Three-part names everywhere; catalog from `config.catalog`.
- `escapeId(name)` — **lowercases** the identifier, then wraps in backticks (Databricks SQL identifier quoting; Postgres/Redshift use double-quotes). Centralizing on `client.escapeId` lets `dol.js`/`sql.js` stay dialect-agnostic — they call `client.escapeId(col)` and the right casing + quoting falls out. See open question #7 for the rationale and the deploy-gate that prevents mixed-case keys from ever reaching this code path.
**Done when:** Unit tests via `proxyquire`-stubbed `@databricks/sql` prove query path, schema describe, identifier lowercasing (`escapeId('OrderId')` → `` `orderid` ``), and error propagation. No live calls.

### Step 5 — `lib/dol.js` and `lib/sql.js` (DDL/DML generation)
- `lib/dol.js`: near-verbatim port of `connectors/postgres/lib/dol.js` (83 lines — superset of the redshift version; extends `leo-connector-common/dol`); absorb identifier-quoting differences via `client.escapeId`. Note: this is the consumer-side query builder, not on the publishing critical path — but cheap to port now.
- `lib/sql.js` (new, pure functions):
  - `createTable(...)` → `CREATE TABLE IF NOT EXISTS … USING DELTA`. Type mapping (audit of all cloned dw_fields found only these scalar types — **no `super`/`json` columns exist in scope**):

    | dw_fields type | Databricks DDL | Notes |
    |---|---|---|
    | `varchar(n)` | `STRING` | Length constraint dropped (Databricks has no length-bounded string type) |
    | `timestamp` | `TIMESTAMP_NTZ` | Timezone-naive; matches Redshift `TIMESTAMP WITHOUT TIME ZONE` semantics |
    | `timestamptz` | `TIMESTAMP` | TZ-aware; matches Redshift `TIMESTAMPTZ` semantics |
    | `date` | `DATE` | |
    | `boolean` | `BOOLEAN` | Stage as `true`/`false` strings in CSV (Step 7), not `0`/`1` — Databricks does not implicitly coerce |
    | `int` / `integer` | `INT` | |
    | `bigint` | `BIGINT` | |
    | `float` | `FLOAT` | Single-precision (FLOAT4 equivalent) |
    | `decimal` (no precision) | `DECIMAL(18,0)` | **Explicit — match Redshift's default. Do NOT rely on Databricks' default of `DECIMAL(10,0)`.** |
    | `decimal(p,s)` | `DECIMAL(p,s)` | Pass through verbatim |

    Always append `_auditdate TIMESTAMP_NTZ`, `_deleted BOOLEAN`. If `clusterKey`, append `CLUSTER BY (clusterKey)`. All identifiers emitted via `client.escapeId` (lowercase + backtick-quoted, per Step 3).
  - `alterAddColumn(...)`, `alterColumnType(...)` (Databricks only widens; throw on narrowing).
  - `mergeFact(target, staging, nks, columnConfig, naturalKeyFilter)` → `MERGE INTO … USING … ON <nk match> [AND target.<clusterKey> >= <naturalKeyFilter>] WHEN MATCHED THEN UPDATE SET … WHEN NOT MATCHED THEN INSERT …`. UPDATE sets each data column to `COALESCE(staging.x, target.x)`, `_deleted=false`, `_auditdate=<auditdate>`.

  **`clusterKey` has two paired purposes** (per [Configuration Migration Analysis](https://www.notion.so/351e0f2aafae8128b7baed05f6a5adbc); coordinate field-name with DPLAT-442 / John Cronin):
  1. **Physical layout** — `CLUSTER BY (clusterKey)` in `createTable` (already covered above).
  2. **MERGE pruning** — `dwconnect.importFact` computes `MIN(clusterKey)` across the staged batch and passes it to `mergeFact` as `naturalKeyFilter`. The added predicate `AND target.<clusterKey> >= <min>` lets Delta skip files (and Redshift skip blocks) whose max for that column falls below the batch's min. Without this, MERGE scans the entire target.

  **"Meaningful ordering within a batch" — what it means in practice:** the pruning helps only when the staged batch's clusterKey values cluster in a *narrow range high in the table's history*. Two things have to be true:
  - **Density** — values within one batch span a small fraction of the table's overall range (otherwise `MIN` ≈ table min, and the filter prunes nothing).
  - **Time-correlation with arrival** — newer events have higher clusterKey values, and batches arrive roughly in time order. Then `MIN(batch)` is far above the table's min and skips most historical files.

  Examples:
  - ✅ `order_id` on `f_order_item` (auto-increment BIGINT): a batch of recent order events sits in a narrow high range; prunes nearly all historical files.
  - ✅ Event-time column on an append-only fact (e.g., the activity-timestamp column on `f_order_item_activity` — confirm exact column name in the table's `dw_fields` before using): same logic.
  - ❌ `account_id`, `retailer_id`: any batch touches many accounts; `MIN` is small and stable; no pruning value.
  - ❌ Categorical columns (status, country_code): no monotonic growth.

  **Fallback** when `clusterKey` is absent (per memory): if the natural key itself has the same properties (single monotonic NK column like `order_id`), use `MIN(nk)`; otherwise emit no filter — never invent ordering.

  `mergeFact` itself should treat `naturalKeyFilter` as opaque: if `null`/`undefined`, omit the extra predicate; otherwise inject it literally as `AND target.<clusterKeyCol> >= <value>`. The decision about *whether* to compute the filter lives in `dwconnect.importFact`, keeping `sql.js` pure.
**Done when:** Snapshot tests cover createTable on `d_order.json`, alterAddColumn, mergeFact on an `f_*` table (with and without `naturalKeyFilter`), every row of the type-mapping table above (`varchar(n)`→`STRING`, `timestamp`→`TIMESTAMP_NTZ`, `timestamptz`→`TIMESTAMP`, `decimal` no-precision→`DECIMAL(18,0)`, `boolean`→`BOOLEAN`, etc.), identifier lowercasing via `escapeId`, `clusterKey` present/absent.

### Step 7 — `lib/dwconnect.js`: `importFact()` hot path

**Caller context worth knowing first:** `general/lib/offload_to_redshift.js:165-247` overrides `client.importFact` — overriding the canonical implementation at `connectors/postgres/lib/dwconnect.js:128` which itself calls `client.streamToTable(...)` for the postgres branch and `client.streamToTableFromS3(...)` for the Redshift branch (`dwconnect.js:204` / `:434`). The S3-staging implementation lives at `connectors/postgres/lib/connect.js:576-…` and is the **primary in-repo reference** for the CSV+S3 staging pattern. (This is in-checkout only after rebasing onto the `development` branch — the package version `leo-connector-postgres@4.0.24-rc` that the Redshift loader actually consumes publishes from `development`, not `master`; per Grant Robinson, all pre-AWS-SDK-v3 connector work ships from `development`.) `item-dw/bots/redshift-loader/redshift-loader.ts:88-96, 582-604` is a confirming second reference — same `fast-csv` + `nonNull` + `ls.toS3` shape, useful for cross-checking parameter choices.

Port the `hashedSurrogateKeys: true` branch from postgres dwconnect (drop the SCD-2 branch — out of scope; `bypassSlowlyChangingDimensions: true`). Steps inside `importFact(stream, table, nks, cb, tableDef)`:

1. **Stage to S3** — produce **byte-identical CSV to what `item-dw/bots/redshift-loader/redshift-loader.ts:582-604` writes**, so the same staged file would feed either pipeline unchanged:
   ```js
   const fastCsv = require('fast-csv');
   function nonNull(v) {                                    // verbatim from postgres/lib/connect.js:394-402 (postgres-direct path); the streamToTableFromS3 nonNull at connect.js:641-653 adds a `version === 'redshift'` branch that escapes `\n` as `\\n` for Redshift COPY — irrelevant here since we mount via read_files(multiLine=>true)
     if (v === '' || v === null || v === undefined) return '\\N';
     if (typeof v === 'string' && v.search(/\r/) !== -1) return v.replace(/\r\n?/g, '\n');
     return v;
   }
   ls.pipeline(
     stream,
     fastCsv.format({
       headers: false,
       delimiter: '|',
       transform: (row, done) => done(null, columns.map(f => nonNull(row[f]))),
     }),
     ls.toS3(dbconfig.s3Bucket, `${dbconfig.s3prefix}/${group}/${table}/${auditdate}.csv`)
   );
   ```
   `columns` comes from the cached describeTable in fixed order. Surrogate key serializes as a decimal string. Boolean values serialize as `true`/`false` strings (Databricks does not implicitly coerce `0`/`1`). Note: this serializer treats `''` as NULL (`\N`) — matches both reference implementations exactly.

   **Open item — S3 staging prefix lookup from Unity Catalog (open question #3):** `dbconfig.s3Bucket` and `dbconfig.s3prefix` must not be static config values. At `connect()` time the connector runs:
   ```sql
   DESCRIBE SCHEMA EXTENDED {catalog}.{schema}
   ```
   Columns are `database_description_item` / `database_description_value`. Find the row where `database_description_item = 'RootLocation'`; its value is the complete staging root URL (e.g. `s3://datalake-dev-641864320185-us-east-1/stage/data/internal/rithum/public_stage`). Parse `s3Bucket` and `s3Prefix` from that and cache them on the client for use in `streamToTableFromS3`.

   Do **not** use the `Location` row — it is an internal UC path with a UUID. Do **not** fall back to `DESCRIBE CATALOG EXTENDED`'s `Storage Root` (`dl/databricks`) — that is a different path convention and would produce a wrong staging location. If `RootLocation` is absent, throw with a clear error rather than construct a wrong path.

   The live bot uses the same mechanism — no S3 config in the caller env.
2. **Mount as temp view**: `CREATE OR REPLACE TEMPORARY VIEW staging_<group>_<table> AS SELECT * FROM read_files('s3://…/<table>/<auditdate>.csv', format=>'csv', sep=>'|', header=>false, quote=>'"', escape=>'"', multiLine=>'true', nullValue=>'\\N', mode=>'PERMISSIVE', schema=>'<col defs>')`. Column list comes from the cached describeTable. Each non-default option chosen for byte-parity with fast-csv's output and Redshift COPY's behavior (verified against the Databricks Auto Loader CSV-options docs):
   - **`escape=>'"'`** — fast-csv@2.4.1 emits RFC-4180-style doubled-quote escaping (`"He said ""hi"""`). Databricks' default `escape='\\'` would mis-parse this. Setting `escape='"'` matches fast-csv's output exactly.
   - **`multiLine=>'true'`** — `nonNull` (Step 7.1) normalizes `\r\n?` → `\n` but lets bare `\n` through unchanged. With the default `multiLine=false`, an embedded `\n` inside a quoted string field would split the row. Redshift COPY with `format csv` handles embedded newlines inside quotes correctly today, so we must too for Step 12 byte-equivalence. Cost: prevents file-split parallelism on the staging file, which is negligible at microbatch sizes.
   - **`nullValue=>'\\N'`** — matches the bare `\N` token fast-csv emits (via `nonNull`) for nulls; also matches Redshift COPY's `NULL AS '\\N'` at `connectors/postgres/lib/dwconnect.js:1247`. Corner case: a string field whose literal value is `\N` will be silently treated as null — same behavior as the existing Redshift pipeline, so byte-equivalent (not a regression).
   - **`mode=>'PERMISSIVE'`** — nulls out individual fields that fail per-column type coercion rather than failing the batch, mirroring `ACCEPTINVCHARS`/`ACCEPTANYDATE` lenient parse semantics. `rescuedDataColumn` is intentionally not enabled — the malformed-record column would diverge from Redshift output. Revisit during the post-coexistence modernization pass.

   **Why temp view + MERGE, not Auto Loader** (Databricks' default recommendation for S3 ingestion): the connector is stateless per batch — RStreams already provides exactly-once delivery and checkpointing via `leo-sdk`, so Auto Loader's file-tracking checkpoint store would duplicate state that's already owned upstream. Temp views also keep the SQL shape identical batch-to-batch (one CREATE VIEW + one MERGE), which simplifies operations, testing, and debugging compared to managing an Auto Loader stream's lifecycle. Revisit only if `read_files` proves unreliable on the staging format at scale; the same CSV format has run in prod via the Redshift loader for years, so the format itself is not the risk.
3. **MERGE INTO**: single statement from `sql.mergeFact(...)`. No two-stage UPDATE/INSERT dance — Databricks MERGE is atomic.
4. **Deletes** (before MERGE, matching Redshift ordering): `UPDATE … SET _deleted=true WHERE <nk> IN (…)` for records flagged with `__leo_delete__`.
5. **Delete staged S3 file** — after the MERGE callback, delete `s3://<bucket>/<key>` via `s3.deleteObject()`. Mirrors `connectors/postgres/lib/connect.js:714-734`. Controlled by `keepS3Files` config option (default `false` — cleanup enabled). Log but do not propagate delete errors. `connect.js` stores `client._lastStagingS3 = { s3, bucket, key }` (set alongside `client._lastStagingView`) when the S3 write stream is opened; `dwconnect.importFact` calls `_cleanupStagedFile` via `mergeCallback` after `_doMerge` resolves.

Keep the `(stream, table, nks, cb, tableDef)` signature so `load.js` doesn't need touching.

**Done when:** Unit test with stubbed connect + stubbed S3: 5-record `d_order`-shaped input asserts one S3 PutObject (body **byte-equal to the output of the same `fast-csv` + `nonNull` pipeline running on the same input** — checked-in golden file), one `CREATE OR REPLACE TEMPORARY VIEW`, one `MERGE INTO public.d_order` with expected ON + SET clauses; delete-flagged record produces UPDATE instead of upsert; boolean column serializes as `true`/`false`; empty-string field serializes as `\N`; row containing a literal `|` in a STRING column is correctly quoted; row containing `\r\n` collapses to `\n`; `s3.deleteObject` is called with the correct bucket+key after a successful MERGE; `keepS3Files: true` skips the `deleteObject` call; a `deleteObject` error is logged but does not propagate to the callback.

### Step 9 — Integration test harness

### Step 12 — Equivalence script (DoD check)
Two complementary checks must both pass before DoD is satisfied:

**(a) Lakebridge reconciliation** — Databricks' supported tool for post-migration validation across the two systems. Run against the same nonprod targets used by the hand-rolled script below. Lakebridge gives broad coverage cheaply: row counts, aggregates, schema parity, and per-column null-rate / min / max / distinct comparisons across the full captured fixture. Sufficient to surface gross drift; insufficient to prove byte-equality on row contents.

**(b) Hand-rolled byte-equal MD5 check** — `test/equivalence/run.js`: one-off Node script (not in `npm test`). Reads a captured prod batch (1k events from the `dim` queue — fact-heavy despite the name, carries most warehouse data — PII-scrubbed) and runs it through both the Redshift loader and the new datalake loader, both targeting the nonprod environments per the Live-write rule. Compares `SELECT <nk>, MD5(CONCAT_WS('|', col1, col2, …))` results row-by-row. Catches the per-row, per-column drift Lakebridge's aggregates won't surface (e.g., decimal-precision shifts, timestamp TZ drift on a single column, off-by-one rounding) and produces actionable diffs on the locked coverage set.

**Table coverage set is TBD — do not invent.** The script asserts equivalence on a list of tables drawn from what the captured fixture populates. Lock the list before running; minimum criteria:
- ≥1 `d_*` and ≥1 `f_*` (dim and fact code paths exercised)
- Type coverage across `varchar(n)→STRING`, `timestamp→TIMESTAMP_NTZ`, integer/bigint, boolean
- ≥1 fact with a `clusterKey` set, so the `naturalKeyFilter` MERGE-pruning path (Step 5) is actually exercised — otherwise that path is silently untested
- Mix of single-column and composite natural keys
- Must be a subset of tables the captured `dim`-queue fixture actually populates

**Done when:** zero diffs on the captured fixture across the locked coverage set. `connectors/datalake/README.md` documents (a) the actual coverage set chosen, (b) the nonprod env names used, (c) repro instructions.

## Risks

1. **`@databricks/sql` binding diff.** Postgres uses `$1`; Databricks uses `?`. Contained to `dwconnect.js` call sites — call out in code review.
2. **`MODIFY` grant.** Step 11 needs ADD COLUMN; pre-check infra grants before running.
3. **Identifier-casing convention drift.** The lowercase-everywhere rule (open question #7) depends on the `bus-models/dw-schema` deploy gate landing alongside the connector. If a producer adds a mixed-case key to dw_fields *before* the gate ships, the connector silently lowercases it on write while Redshift tolerates either casing — consumer queries that case-match Redshift will diverge on Databricks. Mitigation: extend `bus-models/dw-schema` with the lowercase assertion as part of Step 1 prerequisites, not as a follow-up.
4. **Bot wiring out of scope.** Without an `offload_to_datalake.js` bot, nothing in production runs this library yet. Plan a follow-up task to create that bot once Steps 1–12 land.
5. **Operational monitors and alerts not migrated.** Existing CloudWatch alarms, Datadog monitors and dashboards, and PagerDuty services watching Redshift pipeline health need counterparts for the Databricks path. Plan a follow-up to inventory existing monitors (see `data-warehouse-tooling/` invoice monitoring Lambda + PagerDuty integrations) and create equivalent Databricks-side alerts and dashboards before Redshift is retired.
6. **Redshift-specific AI Arcanum skills not migrated.** Any skills in AI Arcanum that embed Redshift SQL, Redshift connection strings, or Redshift-specific procedures will produce wrong output once the Databricks pipeline is live. Plan a follow-up to audit AI Arcanum for Redshift-targeted skills and update or replace them with Databricks-dialect equivalents.
